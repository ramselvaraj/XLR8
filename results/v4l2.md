# V4L2 device (Phase 9)

Run 2026-11-08 on the PYNQ-Z2 (kernel 5.15.19, hardware 0.2.0, PL clock 50 MHz) with
`tools/board/run_driver_tests.sh 300 2000`. Sources: `driver/xlr8_v4l2.c`, `driver/xlr8_blur_fw.h`
(generated by `tools/gen_blur_fw.py`), tests `driver/tests/v4l2_test.c`.

The GPU appears as `/dev/video0` (card "XLR8 GPU 3x3 blur"), a V4L2 memory-to-memory device: queue a
64x64 `XBGR32` image on the OUTPUT queue and a buffer on the CAPTURE queue, and the GPU returns the
3x3 blur of the image. The GPU reads and writes the V4L2 buffers directly in DDR (its memory window
covers both), with no copy.

| Test | Result |
|---|---|
| Capabilities and formats | driver `xlr8`, `VIDEO_M2M` and `STREAMING`, one format (XBGR32) on both queues, `S_FMT` with another size or format is forced to 64x64 XBGR32, `ENUM_FRAMESIZES` reports 64x64 |
| Errors | `STREAMON` with no buffers, `QBUF` before `REQBUFS`, `QBUF` with a bad index, USERPTR: all rejected; the device works afterwards |
| Streaming | 300 frames, every CAPTURE frame equal to the CPU blur, sequence numbers and `bytesused` correct, **53.7 frames/s** |
| DMABUF | a CAPTURE buffer exported with `VIDIOC_EXPBUF` shows the same pixels when mapped through the dma-buf fd |
| STREAMOFF | 10 `STREAMOFF`s with buffers queued at different points, then 20 exact frames |
| Killed streamers | 6 streamers killed with SIGKILL while jobs were queued; the device keeps working |
| Concurrent | 3 V4L2 streamers (60 frames each, different images) plus a `/dev/xlr8` ball renderer at the same time, all exact |
| Leak | 300 open / REQBUFS / mmap / close cycles with no CMA loss |
| Core regression | the full `/dev/xlr8` suite (frames, arguments, bad arguments, timeout, poll, 4 processes, kill, watchdog, 2,000 open/close) still passes on the refactored driver |

The V4L2 frame rate equals the GPU's blur time (about 18.6 ms per frame; see `benchmarks.md` for the
same kernel through `/dev/xlr8`), so the V4L2 layer adds no measurable overhead.

## Build

The board kernel has V4L2 and `videobuf2-dma-contig` built in but not the mem2mem framework, so
`driver/third_party/v4l2-mem2mem.c` (upstream v5.15.19, unmodified) is built as a module beside the
two XLR8 modules. Load order: `v4l2-mem2mem.ko`, `xlr8.ko`, `xlr8_v4l2.ko` (done by
`tools/board/load_xlr8.sh`).

## Bugs found while building it

- **Missing wakeups.** The core driver woke waiters with `wake_up_interruptible_all`, which does not
  wake uninterruptible sleepers. Kernel-side jobs sleep uninterruptibly, so each launch waited out
  its 4 s timeout (an 8 s "blur"), and a job arriving while the GPU was busy could wait forever,
  which hung several processes. Fixed with `wake_up_all`.
- **Unset `fh->m2m_ctx`.** The `v4l2_m2m_ioctl_*` helpers read it; without it `STREAMON` was a NULL
  dereference.
- **Shared program RAM.** V4L2 jobs load the blur program for every job, which overwrote the program
  a `/dev/xlr8` client had loaded earlier. The driver now keeps each file's program and reloads it at
  `SUBMIT` whenever the RAM holds someone else's.

A `dma_alloc_coherent ... failed` line appears in `dmesg` when a streamer is killed while its
buffers are being allocated; vb2 prints it when the allocation is interrupted by the fatal signal.
